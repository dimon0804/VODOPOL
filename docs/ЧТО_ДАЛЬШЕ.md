# Что тестировать и что ещё можно сделать

Живой документ на оставшееся время. Каждый пункт — с оценкой, сколько стоит и что
даёт. Порядок внутри разделов по убыванию отдачи, а не по удобству.

---

## 1. Что проверить до сдачи

Это не «хорошо бы», а то, что жюри сделает само. Лучше споткнуться самим.

### 1.1. Прогон с нуля на чужой машине · 40 минут · блокер, если не сделать

Жюри клонирует репозиторий на пустую машину. Всё, что у нас работает «потому что уже
лежало», там развалится.

```bash
git clone https://github.com/dimon0804/VODOPOL.git /tmp/proverka
cd /tmp/proverka
pip install -r requirements.txt
python -m pytest tests/ -q                 # ожидаем 210 passed
python -m src.api                          # панель на 8000 без данных и без комплекта?
python -m src.cli.fetch_data               # 700 МБ, минут пять
python -m src.validate_bundle outputs/20260926-India_900498-b6000
```

**На что смотреть:** ставятся ли зависимости на чистом окружении; поднимается ли панель
до выгрузки данных; не падают ли тесты, которым нужен комплект; совпадает ли число
тестов с обещанным в README.

### 1.2. Жюри выбирает свой чип · 10 минут · критерий 11

В постановке прямо сказано: жюри вправе взять любой доступный S1-чип официального
набора и запустить обученное решение без повторной подгонки.

```bash
python -m src.cli.run_bundle --chip Spain_7370579 --budget 6000
python -m src.cli.run_bundle --chip Somalia_54221 --budget 6000
python -m src.validate_bundle outputs/<новый_run_id>
```

Взять по чипу из каждой части сплита и один из holdout. **Красный флаг:** любое
падение, любая проверка валидатора кроме OK, любое пустое поле там, где его быть не
должно.

### 1.3. Крайние бюджеты · 5 минут

```bash
python -m src.cli.run_bundle --chip India_900498 --budget 0
python -m src.cli.run_bundle --chip India_900498 --budget 100
python -m src.cli.run_bundle --chip India_900498 --budget 500000
```

**Ожидаем:** при нуле и сотне план C пуст, пакет собирается, валидатор зелёный, статус
неопределённости у C остаётся `scenario`. При полумиллионе B укладывается в бюджет и
перестаёт быть контрфактической.

### 1.4. Панель в браузере · 15 минут · критерий 19

Пройти руками весь сценарий защиты и смотреть в консоль браузера, а не только на
экран:

- переключить все четыре слоя, проверить легенду у каждого;
- подвигать слайдер бюджета быстро туда-сюда — нет ли гонки ответов, не отстаёт ли
  таблица от карты;
- кликнуть по каждой из десяти точек и по нескольким зонам, проверить попапы;
- нажать выгрузку комплекта, открыть архив, убедиться, что внутри двенадцать файлов;
- открыть на узком окне (1280 px) — не разъезжается ли вёрстка;
- перезагрузить страницу с `Ctrl+F5` и убедиться, что подхватились свежие статика и
  данные.

**Красный флаг:** любая ошибка в консоли, любое число без пометки происхождения.

### 1.5. Docker на чистом контексте · 15 минут

```bash
docker compose down -v && docker compose up -d --build
docker compose ps            # ожидаем healthy
curl -s localhost:8000/api/health
```

Проверить отдельно: поднимается ли панель, если каталога `data/cache` нет вовсе.
Подложки S1 не будет, всё остальное должно работать и честно об этом сказать.

### 1.6. Репетиция демо · 30 минут · самое недооценённое

Прогнать сценарий из вольта вслух, по часам, с тремя вбросами от того, кто играет
жюри:

1. «Поменяйте бюджет на 12 тысяч» — должно занять секунды;
2. «Запустите на другом чипе» — команда должна быть под рукой, не надо её сочинять;
3. «Как вы получили координаты объектов?» — ответ с открытым `run_metadata.json`.

Если любое из трёх занимает больше минуты — это дефект продукта, а не защиты, и чинить
надо код.

## 2. Модель: что ещё можно попробовать

Три гипотезы подряд отклонены, дешёвые идеи кончились. Оставшиеся — дороже, и браться
за них стоит только если останется время после раздела 1.

### 2.1. Калибровка по сцене · 2 часа · отдача средняя, риск средний

**Проблема, которая это оправдывает.** На тесте ECE 0,024, на отложенном событии 0,097
— вчетверо хуже. Глобальный калибратор обучен на трёх событиях validation и на новом
регионе уезжает.

**Что делать.** Приводить сырой выход модели к собственному распределению чипа
(квантильная нормализация) перед изотонической калибровкой. Проверять на validation —
она и есть набор невиданных событий, так что это честный тест переноса.

**Чем рискуем.** На чипе, где воды нет вовсе, нормализация заставит модель её
придумать. Нужен предохранитель: не нормализовать, если доля тёмных пикселей ниже
порога. Без предохранителя лучше не трогать.

### 2.2. Компактный U-Net · 4 часа · отдача неизвестна, риск высокий

Единственная ветка, где возможен скачок, а не десятые доли: свёрточная сеть видит
форму разлива, а не только статистику окна.

**Реальность.** 4 ГБ видеопамяти, батч 2–4 на 512×512, установка torch плюс обучение.
Если не уложиться — останемся без времени на всё остальное. Браться, только если
раздел 1 закрыт полностью и до сдачи больше пяти часов.

### 2.3. Слабая разметка как добавка · 3 часа · отдача под вопросом

В наборе есть `WeaklyLabeled` — тысячи чипов. Соблазн большой, но разметка там
получена порогом Оцу, то есть модель будет учиться подражать тому самому методу,
который мы пытаемся обойти. Имеет смысл только как предобучение с последующей
дообучкой на ручной разметке, и это уже полноценный эксперимент.

### 2.4. Что пробовать НЕ надо

Проверено и отклонено, повторять не нужно: нормировка каналов на статистику чипа,
медианная фильтрация каналов, разложение на две головы, смесь с пороговым методом,
снижение доли положительных пикселей. Все пять — в журнале с числами.

## 3. Сервис: что ещё можно сделать

### 3.1. Панель на домене · зона Никиты · критерий 19

Скрипты готовы, нужна DNS-запись на `vodopol.clv-digital.tech`. Живая ссылка в README
сильно убедительнее инструкции: жюри откроет её со своего ноутбука, не собирая ничего.

### 3.2. Экспорт карты в PNG для презентации · 30 минут

Кнопка «сохранить текущий вид карты» — чтобы слайды делались из самого продукта, а не
скриншотами. Мелочь, но на защите видно.

### 3.3. Показ обеих голов и слоя ошибок · 1 час

Сейчас на карте есть вероятность, маска и неопределённость. Полезно добавить слой
«где мы ошиблись относительно ручной метки» для чипов, где разметка есть. Это прямо
отвечает на вопрос критерия 4 про ложные срабатывания и пропуски — не словами, а
картинкой.

### 3.4. Подпись даты съёмки чипа на экране · 15 минут

В паспорте запуска дата есть, на экране только срок решения. Жюри спросит, когда снят
чип, — пусть будет видно сразу.

## 4. Защита

### 4.1. Забрать у организаторов типовые формы и вопросы · сделать первым

Постановщик на отраслевой сессии сказал, что они собраны. У нас их нет. Спросить
трекера — это дешевле любого эксперимента и может закрыть пункты, о которых мы не
знаем.

### 4.2. Отрепетировать один трудный ответ

Самый вероятный неудобный вопрос: «почему ваш метод проигрывает порогу по F1».
Ответ есть и он честный — втрое меньше ложных срабатываний на постоянной воде,
калиброванные вероятности, проверенная неопределённость, без которых экономический
контур не строится вообще. Но его надо сказать спокойно и за двадцать секунд, а не
искать на ходу.

### 4.3. Один слайд с отклонёнными гипотезами

Пять отклонённых против трёх принятых — это не слабость, это доказательство, что
конфигурация выбрана измерением. Такой слайд отличает команду, которая проверяла, от
команды, которая угадала.
