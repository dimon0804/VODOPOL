# Водополь

**Оценка экономического ущерба от паводка по радарному снимку Sentinel-1 и обоснование
заказа дополнительной съёмки в пределах бюджета.**

КосмоХакатон 2026, кейс 2 «ИИ-оценка экономического ущерба от паводка и оптимизация
заказа ДЗЗ». Команда CLV-DIGITAL.

«Водополь» — устаревшее и областное русское слово для половодья, разлива.

## Что делает система

```
S1-чип (VV/VH, дБ)
      ├─► пороговый baseline ──────────────► бинарная маска ──┐
      └─► основной метод ─► вероятность ──► маска по порогу ──┴─► сравнение
                                 │
                        10 объектов (seed) ─► EL = p × V × q ─► ранги проверки
                                 │
                       кандидатные зоны ─► цена по ПП РФ № 840 ─► A / B / C при бюджете
```

Смена бюджета пересчитывает план закупки **без переобучения модели и без изменения
порога бинаризации**: меняются только отбор зон, стоимость и сравнение стратегий.

## Данные

Единственный обязательный источник — официальный
[Sen1Floods11](https://github.com/cloudtostreet/Sen1Floods11), версия `v1.1`.
В репозиторий набор не выкладывается: он берётся из официального бакета.

```bash
python -m src.cli.fetch_data
```

Качается только размеченная часть: 446 чипов × 4 слоя (`S1Hand`, `LabelHand`,
`JRCWaterHand`, `S1OtsuLabelHand`), около 700 МБ. Полные 14 ГБ со слабой разметкой не
нужны. Бакет публичный, `gsutil` и учётные данные не требуются.

Дополнительных источников данных нет: решение работает **только по Sentinel-1**.
Слой `JRCWaterHand` используется на стороне разметки для выделения целевого класса, а
на применении модели не требуется — это проверяется запуском на любом чипе.

## Запуск за две команды

```bash
pip install -r requirements.txt
python -m src.api            # панель на http://localhost:8000
```


Панель сама находит свежий комплект в `outputs/`. Комплект, открытый при старте,
задаётся переменной `FLOODVALUE_RUN`.

**Чип переключается прямо в панели.** Выпадающий список в шапке перечисляет все
собранные комплекты из `outputs/` и подписывает каждый датой съёмки и ролью события
в протоколе — «обучение» или «независимая проверка», чтобы было видно, показывается
результат на знакомых модели данных или на новых. Выбор попадает в адресную строку
(`?run=<run_id>`), поэтому ссылка на конкретный чип пересылается и открывается как
есть. Собрать ещё один комплект и увидеть его в списке без перезапуска сервиса:

```bash
python -m src.cli.run_bundle --chip Pakistan_132143 --budget 6000
```

Переключение чипа перечитывает готовые файлы комплекта. Модель при этом не
переобучается, порог не пересчитывается — ровно как и при смене бюджета.

**Новый комплект собирается тоже из панели.** Кнопка «+ чип» рядом со списком
открывает окно, где выбирается чип из выкачанного каталога (446 штук, с фильтром
по событию и подписью роли в протоколе) и объявленный бюджет. Сервис запускает ту
же самую команду `run_bundle`, что человек набрал бы в терминале, и показывает её
протокол построчно по мере выполнения — включая итог валидатора. Прогон занимает
около полминуты, после него панель сама открывается на новом комплекте.

Границы этой кнопки названы честно: собирать можно только чипы, уже лежащие в
`data/cache` (иначе сборка обещала бы то, чего нет на диске), одновременно идёт не
больше одного прогона, идентификатор чипа проверяется по каталогу, бюджет — по
диапазону. Если каталог `outputs/` смонтирован только на чтение, кнопка гаснет
сразу с объяснением, а не падает на середине прогона.

### В Docker — если не хочется ставить зависимости

```bash
docker compose up --build
```

Панель на <http://localhost:8000>. Больше ничего делать не нужно: комплекты запусков и
веса монтируются из репозитория, поэтому новый прогон подхватывается перезапуском
контейнера, без `docker build`.

Образ намеренно не содержит ни исходного набора, ни комплектов: внутрь кладётся только
код. Контейнер работает под непривилегированным пользователем, ничего не пишет и имеет
healthcheck — состояние видно в `docker compose ps`.

Каталог `data/cache` монтируется ради подложки S1: исходный чип `S1Hand` в комплект
запуска не входит. Если датасет не выкачан, каталог пустой — панель работает, подложки
нет, остальные слои карты не затронуты.

Проверено запуском: образ собирается, контейнер поднимается, панель отвечает, подложка S1 и все тематические слои отдаются изнутри контейнера.

## Что именно сдано: коммит и контрольные суммы

Требование «по репозиторию можно воспроизвести результат» держится на двух вещах,
которые легко потерять: на конкретной ревизии кода и на тех самых весах.

```bash
git rev-parse HEAD                      # ревизия, на которой собраны комплекты
python -m src.cli.verify_weights        # сверка весов с models/CHECKSUMS.txt
```

Ревизию не зашиваем в текст руками: она записывается в каждый комплект сама, поле
`commit` в `run_metadata.json`. Значит, к какому состоянию кода относится любой
сданный результат, видно из самого результата, а не из обещания в README.

Веса лежат в репозитории, но «лежат» и «те самые» — разные утверждения: файл мог
перезаписать неудачный прогон обучения. `models/CHECKSUMS.txt` хранит SHA-256, а
команда выше отвечает одной строкой. После сознательного переобучения суммы
обновляются флагом `--update` и коммитятся вместе с весами.

## Воспроизводимость

Точный коммит проверяемой копии — тот, что вы склонировали:

```bash
git rev-parse HEAD
```

Хардкодить его в этом файле бессмысленно: любая правка README меняет коммит, и
записанное значение устаревает в тот же момент. Материалы в `reports/` и веса в
`models/` соответствуют состоянию репозитория на момент последнего изменения этих
каталогов — оно видно в `git log -1 -- reports/ models/`.

**Нужен Python 3.12 или новее.** Версии в `requirements.txt` закреплены точно, потому что
веса сохранены через pickle и чувствительны к версиям scikit-learn и LightGBM, а
закреплённый `numpy==2.5.1` на Python 3.10 и 3.11 не ставится вовсе. Если под рукой
другой Python — используйте Docker, в образе 3.12.

Тесты, запуск панели на готовых комплектах и сборка образа проверены на Python 3.12
с версиями из `requirements.txt`. Список версий здесь не дублируется: источник
истины — сам `requirements.txt`.

Числовые результаты в этом файле не дублируются намеренно: модель переобучается, и
копия метрик в README расходится с фактом быстрее, чем её успевают поправить. Живые
значения — в [`reports/metrics_main_validation.json`](reports/metrics_main_validation.json)
и [`reports/comparison.md`](reports/comparison.md), сводка — в
[`reports/report.md`](reports/report.md).

### Цель запуска меняет цену

Эксперты кейса заметили верное: от цели заказа зависят затраты. Это не лозунг, а
устройство ПП РФ № 840 — за срочность платят коэффициентом актуальности.

```bash
python -m src.cli.run_bundle --chip India_900498 --budget 6000 --purpose damage
```

| Цель | Кто заказывает | Съёмка | Ставка, ₽/км² | Широкая закупка B |
| --- | --- | --- | ---: | ---: |
| `response` — оперативное реагирование | дежурный по паводку | новая | 1 703,46 | 49 059,60 |
| `damage` — оценка ущерба для компенсаций | экономист-оценщик | архивная | 567,82 | 16 353,20 |
| `planning` — планирование защитных сооружений | проектировщик | архивная, L1, неограниченный режим | 709,78 | 20 441,60 |

Разница между первой и второй строкой ровно трёхкратная, и это не наша натяжка:
коэффициент актуальности 1,8 против 0,6. Дежурному архив бесполезен — вода уже
ушла; оценщику ущерба, наоборот, нужна сцена из пика разлива, которая к моменту
расчёта выплат уже стала архивной, и переплачивать за срочность ему незачем.

Цель попадает в паспорт запуска и в имя каталога, так что два прогона по одному
чипу с разными целями не затирают друг друга — а сравнивают как раз их цену.

### Снимок и источники из-за пределов набора

Обучение привязано к Sen1Floods11 по определению — модель училась именно на нём.
Применение не привязано ни к чему: на вход идут два канала радарного снимка в
децибелах, и откуда взялся файл, модели безразлично.

```bash
# тот же расчёт на снимке из Copernicus, ASF или архива оператора
python -m src.cli.run_bundle --chip Ob_2026_04 --budget 250000     --s1-file scenes/ob_2026_04.tif --sources config/sources.json
```

Требования к файлу проверяются на входе и объясняются словами, а не трейсбеком:
GeoTIFF 512×512, два канала VV и VH, значения в дБ, шаг сетки около десяти метров.
Если подать линейную интенсивность вместо децибел или кадр другого размера, запуск
остановится с объяснением, что именно не так и что с этим делать.

Чего такой запуск честно **не** делает: не считает метрики качества. Ручной разметки
к чужому снимку нет, сравнивать не с чем, и в паспорте запуска стоит пометка
`input_source.kind = external` вместе с прямым предупреждением, что применимость
модели к этому источнику не измерена.

Дополнительные источники — слой зданий, архивная оптика, снимок оператора —
объявляются файлом и целиком попадают в `source_manifest.json`. Образец с полями и
пояснениями: `config/sources.example.json`. Мы ничего не додумываем за того, кто
запускает: дату съёмки и лицензию он указывает сам, выдуманные были бы хуже пустых.

один раз, после фиксации модели.

## Целевой класс

Метка `1` в Sen1Floods11 означает воду вообще: река и озеро помечены так же, как разлив.
Мы оцениваем **временное затопление**: `LabelHand == 1 AND JRCWaterHand == 0`.

Источник постоянной воды — слой `JRCWaterHand` из самого официального набора
(JRC Global Surface Water, построен по Landsat 1984–2020, то есть до событий набора
2016–2019: временная корректность соблюдена). На контрольном чипе `India_900498` из
123 953 пикселей воды 52 397 оказались постоянной — 42 %. Без этого
шага ожидаемый ущерб систематически завышается.

Дособытийной истории Sentinel-1 по тем же контурам в официальном наборе нет, поэтому
подтверждение по истории S1 не выполнялось и в отчёте обозначено как ограничение.

## Работа без вспомогательных данных

**Sentinel-2 в решении не используется вообще.** Ни один слой оптики не входит ни в
обучение, ни в применение, поэтому отдельное сравнение «S1-only против расширенного
варианта» не проводится: расширенного варианта не существует. Это сознательный выбор,
а не упущение — организаторы на отраслевой сессии прямо просили не набирать источники
ради их числа, а решение обязано работать по одному Sentinel-1.

Что это означает практически: облачность на результат не влияет никак, и отсутствие
пригодной оптики над территорией не мешает получить карту.

Проверить режим можно буквально: достаточно каталога с одним слоем.

```bash
python -m src.cli.s1_only --chip Bolivia_103757
```

Команда копирует во временный каталог **только** файл `S1Hand`, читает чип оттуда и
считает вероятность. Ни `LabelHand`, ни `JRCWaterHand` рядом нет.

Слой меток при этом остаётся `None`, вероятность и неопределённость считаются, метрики —
нет: без ручной разметки качество измерить нечем, и код об этом сообщает явно, а не
подменяет цель молча. `JRCWaterHand` нужен только на стороне разметки при обучении.

### Когда качество падает

Условия заявляем заранее, а не после вопроса жюри:

- **ветровая рябь на открытой воде** поднимает обратное рассеяние, и вода перестаёт
  быть тёмной — пропуски;
- **тени рельефа и радарная тень** дают тёмные области там, где воды нет — ложные
  срабатывания; контекстные признаки часть таких случаев снимают, но не все;
- **гладкие сухие поверхности** — асфальт, солончаки, сухой песок — выглядят как вода
  в обоих каналах;
- **застройка и растительность над водой** прячут затопление: двойное отражение от
  стен и стволов возвращает сильный сигнал поверх воды;
- **угол падения и орбита** меняют абсолютный уровень сигнала между сценами; модель
  обучена на четырёх событиях, и на геометрии съёмки, далёкой от обучающей, качество
  снижается — это видно на отложенном событии и записано в отчёте;
- **мелкая вода среди растительности** на радаре почти не отличается от суши.

## Два метода

**Baseline** — пороговый по Sentinel-1. Канал, порог и размер медианного фильтра
выбраны перебором на validation по гистограммам (`src/cli/train_baseline.py`).

**Основной метод** — ансамбль LightGBM по пиксельным признакам с пространственным
контекстом на четырёх масштабах (окна 3, 9, 25, 51 пикселей), изотоническая калибровка
вероятностей на validation, оценка неопределённости. Порог применяется **после**
модели и только для получения согласованной бинарной маски.

Что это не «другой порог», подтверждено экспериментом E02: та же модель только на
VV и VH даёт F1 0,52, с контекстными признаками — 0,63. Прирост даёт именно
окрестность.

## Экономика заказа

Цена считается по ПП РФ № 840 в редакции от 27.08.2025:

```
РП = Б × К × О × П × Т × Р
```

Все множители выходят в `procurement_plan.csv` отдельными колонками — цену любой
позиции можно пересчитать на калькуляторе. Реализация на `Decimal` с ROUND_HALF_UP,
контрольные примеры постановки воспроизводятся знак в знак: 1 703,46 при новой
гарантированной покупке, 946,37 при оперативной съёмке, 567,82 при архиве
(`tests/test_pricing.py`).

**Ставка Б = 788,64 руб./км² — сценарная.** Подтверждённого действующего размера БРЕ
в материалах кейса нет, поэтому во всех файлах и на экране стоит
`base_rate_status = scenario`. Официальным тарифом это число не называется.

Скидка Р пересчитывается для корзины целиком: добавление зоны меняет суммарную площадь
группы, а значит и цену всех остальных позиций. Складывать заранее посчитанные цены
одиночных зон нельзя, и тест это стережёт.

## Панель оператора

Обычный Leaflet, без сборщиков и фреймворков. Всё на одном экране:

- **карта** — подложка S1 в дБ, поверх переключаемые слои: вероятность затопления с
  легендой, бинарная маска, неопределённость; регулятор прозрачности;
- **десять объектов** портфеля точками, размер и цвет по рангу ожидаемого ущерба, рядом
  таблица, отсортированная по ущербу;
- **зоны съёмки** — весь каталог светлым контуром, выбранные текущей стратегией
  заливкой; клик по зоне раскрывает цену с разложением по множителям ПП 840, площадь,
  срок и параметры заказа;
- **слайдер бюджета** — главный интерактив; пересчитываются только отбор зон, стоимость
  и сравнение, о чём под слайдером написано прямым текстом;
- **таблица A/B/C** и таблица чувствительности;
- **кривая «бюджет → покрытый ущерб»** по стратегии C — от нуля до стоимости полной
  закупки, с точкой насыщения, после которой доплачивать бессмысленно. Каждая точка —
  тот же пересчёт `/api/strategies?budget=`, что за слайдером; кривая помечена
  сценарной, потому что цены зон идут по сценарной ставке БРЕ;
- **наряд на обследование** — печатная страница и CSV: объекты в порядке ранга
  ущерба с координатами и отметкой, попадают ли они в заказанную съёмку и в какие
  зоны. Рабочий документ для бригады, а не скриншот;
- **заявка на съёмку** — корзина выбранной стратегии как печатный документ заказа: по
  позиции на зону контур, сенсор, даты, все множители РП = Б × К × О × П × Т × Р, цена
  и итог; плашка о сценарной ставке, у B сверх бюджета штамп «контрфактическая»;
- **объяснение объекта** — в попапе цепочка «от пикселя до рубля»: p из растра в
  пикселе объекта, V и q из кейса, EL = p × V × q с числами, положение на маске с
  оговоркой, что на ущерб оно не влияет, и какой зоной объект проверяется;
- **таймлайн «успеете ли к сроку»** — даты съёмки и доступности зон против срока
  решения: видно, что архив до события и опоздавшие данные в покрытие не идут;
- **кнопка выгрузки комплекта**.

Рядом с каждым числом стоит пометка, откуда оно: расчёт модели, сценарное, условие
кейса, измерено или нет оценки. Ставка БРЕ помечена сценарной на экране, а не в
подсказке. Стратегия B, если вышла за бюджет, помечается контрфактической с объяснением,
почему она показана.

Ролевых профилей пользователей нет сознательно: организаторы просили не заигрываться.

### Контракт API

Слой API не вычисляет ничего сам — он вызывает методы `src/runtime.py` и сериализует
результат. Поэтому числа на экране не могут разойтись с файлами комплекта.

| Путь | Отдаёт |
| --- | --- |
| `GET /api/health` | состояние сервиса, версия, загруженный `run_id` |
| `GET /api/runs` | собранные комплекты: чип, дата съёмки, роль события, бюджет |
| `GET /api/chips` | каталог выкачанных чипов и признак, можно ли здесь собирать |
| `POST /api/build` | запустить сборку комплекта: `{chip_id, budget_rub}` |
| `GET /api/build/{job_id}` | ход сборки: статус, протокол команды, итоговый `run_id` |
| `GET /api/run` | паспорт запуска |
| `GET /api/assets` | объекты портфеля с `p`, ущербом, неопределённостью, рангом |
| `GET /api/candidates` | каталог зон дополнительной съёмки |
| `GET /api/strategies?budget=` | сравнение стратегий A/B/C под заданный бюджет |
| `GET /api/sensitivity` | таблица чувствительности |
| `GET /api/raster/{kind}.png` | слой карты PNG, границы в заголовке `X-Bounds` |
| `GET /api/bundle.zip` | комплект запуска одним архивом |

Все ручки данных принимают параметр `run=<run_id>` — тот же, что кладёт в адрес
выпадающий список панели. Без параметра отвечает комплект, открытый по умолчанию.
Идентификатор проверяется по перечню каталогов в `outputs/`: выйти за него
параметром нельзя, несуществующий комплект отвечает 404 с объяснением.

`kind` — один из `s1`, `probability`, `mask`, `uncertainty`.

## Развёртывание на сервере

```bash
git clone https://github.com/dimon0804/VODOPOL.git ~/vodopol
cd ~/vodopol && bash deploy/deploy.sh          # сборка, запуск, проверка живости
bash deploy/setup-nginx.sh                     # обратный прокси и сертификат
```

Контейнер слушает только на локальном адресе, наружу отдаёт nginx: у приложения нет
забот про TLS. Оба скрипта идемпотентны, повторный запуск обновляет и перезапускает.
`setup-nginx.sh` отдельно проверяет, что заголовок `X-Bounds` доходит через прокси —
без него карта открывается пустой, и ни одной ошибки в консоли браузера при этом нет.

## Тесты

```bash
pip install -r requirements-dev.txt
python -m pytest tests/ -q
```

С выкачанным набором ожидаемо **223 пройденных**. На чистой машине без набора часть
тестов пропускается: им нужны исходные чипы и собранный комплект. Пропуск, а не
падение — сознательное решение: репозиторий должен проверяться без 700 МБ скачивания.
После `python -m src.cli.fetch_data` и одного прогона `run_bundle` пропусков не
остаётся.

Зависимости прогона тестов вынесены в отдельный файл и в образ не попадают: `pytest` и
HTTP-клиент для `fastapi.testclient` не нужны работающей панели. Без
`requirements-dev.txt` файл `tests/test_api.py` не собирается и обрывает весь прогон на
импорте.

Что покрыто: арифметика цены и границы коэффициентов, геометрия зон и площадь через
EPSG:6933, размещение объектов и расчёт ущерба, стратегии и двойной учёт покрытия,
чувствительность, сборка и проверка пакета, API.

## Границы прототипа

План проверки на других событиях и реальных объектах — в [`reports/report.md`](reports/report.md), раздел 8а.


- Один демонстрационный чип; перенос на тысячи километров и реальные реестры
  инфраструктуры — предмет последующего развития.
- Стоимости V и уязвимости q учебные, заданы постановкой, к реальному имуществу на
  территории чипа отношения не имеют.
- Ставка съёмки и даты доступности сценарные; применимость правового режима к реальному
  заказу требует отдельного подтверждения.
- Фактической покупки данных не было: эффект закупки — сценарий, а не измерение.
  Снижение совокупных потерь не заявляется.
- Отделение постоянной воды опирается на JRC — производный продукт по оптике Landsat со
  своей ошибкой на узких реках и мелководье.
- Прототип не является официальной оценкой ущерба.

Ограничения самого сервиса, чтобы они не всплыли на показе:

- **Подложка S1 требует выкачанного набора.** `/api/raster/s1.png` строится из файла
  `S1Hand`, который лежит в `data/cache/` и в комплект запуска не входит. Без
  `python -m src.cli.fetch_data` ручка отвечает 503 с объяснением: карта работает без
  радарной подложки, тематические слои не затронуты. В Docker каталог монтируется, так
  что достаточно выкачать набор на хосте.
